# Scenario 01: Troubleshooting a Sudden 4x Runtime Spike in a 500 GB Databricks Job

## Problem Statement
A daily Databricks batch job processing ~500 GB has historically run in 30 minutes. Suddenly, without code changes, the runtime spikes to 2 hours. How do you systematically troubleshoot, identify the root cause, and optimize it?


## 1. Systematic Triage Workflow

```
[ Job Runtime Spike: 30m ──> 2h ]
               │
               ▼
[ 1. Check Input Volume & Source Drift ] ──> Did input rows/bytes explode (e.g., 500GB ──> 2TB)?
               │
               ▼
[ 2. Spark UI Triage ]
       ├── Stage Event Timeline ──> Long GC pauses? Straggler tasks?
       ├── Executor Tab        ──> Dead/restarting executors? Spot instance preemptions?
       └── Stages Tab          ──> Shuffle Spills (Memory/Disk)? Skewed max task duration?
               │
               ▼
[ 3. Storage & Delta Log Health ] ──> Small files? Uncompacted Delta transaction log?
```


## 2. Root Cause Analysis & Resolutions

### Root Cause A: Severe Data Skew on a Join/Group Key
- **Spark UI Indicator:** In the slowest Stage, 199 tasks finish in 5 seconds, but 1 task runs for 1.5 hours.
- **Cause:** Upstream data contained a massive spike of `NULL` keys, default placeholder keys (`"UNKNOWN"`), or a viral customer/merchant account.
- **Solution:**
  1. Enable Adaptive Query Execution (AQE) Skew Join:
     ```python
     spark.conf.set("spark.sql.adaptive.enabled", "true")
     spark.conf.set("spark.sql.adaptive.skewJoin.enabled", "true")
     ```
  2. Isolate/Filter `NULL` keys before joins or apply **Salting** on the skewed key.


### Root Cause B: Disk & Memory Spill in Shuffle Stage
- **Spark UI Indicator:** `Spill (Disk)` shows 200+ GB spilled in `ShuffleExchangeExec`.
- **Cause:** Default `spark.sql.shuffle.partitions` (200) meant each partition held >2.5 GB of uncompressed data, exceeding executor memory.
- **Solution:**
  1. Dynamically tune shuffle partitions to target 100–200 MB per partition:
     ```python
     # 500GB / 150MB ≈ 3300 partitions
     spark.conf.set("spark.sql.shuffle.partitions", "3000")
     spark.conf.set("spark.sql.adaptive.coalescePartitions.enabled", "true")
     ```


### Root Cause C: Spot Instance Preemption & Cluster Resizing
- **Indicator:** In the **Executors** tab, node IDs change frequently with multiple task retry attempts (`FetchFailedException`).
- **Cause:** High cloud spot-market preemption killed worker nodes mid-shuffle, forcing Spark to recompute upstream stages from scratch.
- **Solution:**
  - Allocate Driver and core worker nodes on **On-Demand VMs**, while keeping only burst auto-scaling workers on Spot VMs.


### Root Cause D: Stale Metadata & Small File Accumulation on Target Table
- **Indicator:** Stage spending excessive time in `Listing leaf files and directories` or writing millions of tiny Parquet files.
- **Solution:**
  1. Run `OPTIMIZE` with `ZORDER`:
     ```sql
     OPTIMIZE target_delta_table ZORDER BY (primary_lookup_key);
     ```
  2. Enable Auto-Compaction and Optimized Writes:
     ```python
     spark.conf.set("spark.databricks.delta.optimizeWrite.enabled", "true")
     spark.conf.set("spark.databricks.delta.autoCompact.enabled", "true")
     ```
