# Scenario 06: Resolving Out-of-Memory (OOM) Errors During Large Spark Joins

## Problem Statement
A Databricks transformation performing a heavy join across large datasets fails with `java.lang.OutOfMemoryError: Java heap space` or `ExecutorLostFailure (exit code 137 / OOMKilled)`. How do you identify whether it is Driver OOM vs Executor OOM, diagnose the cause, and optimize the join?


## 1. Step 1: Diagnose Driver OOM vs Executor OOM

```
                                [ OOM Failure Detected ]
                                           │
             ┌─────────────────────────────┴─────────────────────────────┐
             ▼                                                           ▼
    [ Driver OOM ]                                              [ Executor OOM (Code 137) ]
    • Symptom: Spark UI crashes / cluster terminates             • Symptom: Stage fails with Task Lost
    • Causes:                                                   • Causes:
      - Calling `.collect()`, `.toPandas()` on large DF            - Severe Data Skew on Join Key
      - Driver broadcasting a table too large (>2GB)               - Massive Shuffle partition size (>2GB JVM limit)
      - Excessive accumulator/broadcast variables                  - Insufficient memory overhead for off-heap/Py4J
```


## 2. Step 2: Key Remediation Strategies for Join OOMs

### Strategy 1: Switch from Cartesian / Nested Loop to Hash / Merge Join
Check if the join condition is missing an equality predicate (`=`), which triggers a disastrous Cartesian Product ($M \times N$ rows):
```python
# ❌ Cartesian Explosion
df_joined = df_fact.join(df_dim) 

# ✅ Standard Hash / Sort-Merge Join
df_joined = df_fact.join(df_dim, on="customer_id", how="inner")
```


### Strategy 2: Mitigate Join Data Skew via Salting
When 1 key (e.g., `customer_id IS NULL` or a top enterprise ID) concentrates millions of rows into a single executor partition:

```python
import pyspark.sql.functions as F

SALT_FACTOR = 8

# Salt the large table
df_large_salted = df_large.withColumn(
    "salt", F.concat(F.col("join_key"), F.lit("_"), F.floor(F.rand() * SALT_FACTOR))
)

# Replicate the small lookup table across all salt keys
df_small_exploded = (
    df_small
    .withColumn("salt_arr", F.array([F.lit(i) for i in range(SALT_FACTOR)]))
    .withColumn("salt_suffix", F.explode("salt_arr"))
    .withColumn("salt", F.concat(F.col("join_key"), F.lit("_"), F.col("salt_suffix")))
    .drop("salt_arr", "salt_suffix")
)

df_result = df_large_salted.join(df_small_exploded, on="salt", how="inner").drop("salt")
```


### Strategy 3: Tune Shuffle Partitions & Memory Overhead
If individual shuffle partitions exceed the 2 GB Spark block limit:
```python
# 1. Increase shuffle partition count
spark.conf.set("spark.sql.shuffle.partitions", "2000")

# 2. Increase executor memory overhead (for off-heap Python worker memory)
spark.conf.set("spark.executor.memoryOverhead", "4g")
```


### Strategy 4: Replace Inefficient Python UDFs with Native PySpark / Vectorized UDFs
Python UDFs serialize row-by-row via Py4J IPC, bloating executor off-heap memory. Replace them with native `pyspark.sql.functions` or Pandas Vectorized UDFs (PyArrow):
```python
from pyspark.sql.functions import pandas_udf
import pandas as pd

@pandas_udf("double")
def calculate_compound_interest(principal: pd.Series, rate: pd.Series) -> pd.Series:
    return principal * (1 + rate) ** 5
```
