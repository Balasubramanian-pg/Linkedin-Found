# Scenario 09: Optimizing Multi-Terabyte Delta Tables for Date-Filtered Queries

## Problem Statement
A core analytical Delta table has reached several terabytes (billions of rows). Analytical queries filtering on `transaction_date` or joining on `customer_id` have slowed down significantly. What Databricks optimization techniques should you apply?


## 1. Diagnostic Analysis: File Pruning & Data Skipping

When a query runs `SELECT * FROM fact_orders WHERE order_date = '2026-08-30'`:
- **Unoptimized State:** The engine scans all 50,000 files in the table (5 TB read from storage).
- **Optimized State:** Through partition pruning and **Delta Data Skipping (Min/Max statistics)**, the engine scans only the 10 relevant files (10 GB read), achieving a 500x speedup.


## 2. Optimization Techniques

### Technique 1: Liquid Clustering (Modern Databricks Recommendation)
In Databricks Runtime 13.3+, **Liquid Clustering** replaces rigid physical partition directories and static Z-Ordering. It dynamically organizes multi-terabyte data without data skew or file explosion:

```sql
-- Convert or create table with Liquid Clustering
ALTER TABLE fact_orders CLUSTER BY (order_date, customer_id);

-- Run periodic incremental clustering
OPTIMIZE fact_orders;
```
- **Benefits:** No fixed partition hierarchy, supports instant column clustering adjustments, avoids partition pruning errors.


### Technique 2: Z-ORDER Clustering (for Delta Tables without Liquid Clustering)
If using classic Delta Lake, Z-Order by date and high-cardinality join keys:

```sql
OPTIMIZE fact_orders
WHERE order_date >= '2026-01-01'
ZORDER BY (order_date, customer_id);
```
> **Data Skipping Internals:** Delta Lake automatically collects min/max statistics for the first 32 columns. Z-Ordering groups similar values into the same Parquet files, allowing Delta to skip 90%+ of files based on footer stats.


### Technique 3: Tune Delta Data Skipping Column Statistics
If the filter column is positioned past the 32nd column in a wide table, Delta Lake does not collect min/max statistics for it by default!

```sql
-- Increase statistics index collection to the first 64 columns
ALTER TABLE fact_orders SET TBLPROPERTIES (
  'delta.dataSkippingNumIndexedCols' = '64'
);
```


### Technique 4: Enable Databricks Photon Engine
Databricks **Photon** is a vectorized query engine rewritten in native C++:
- Delivers 3x to 8x faster query execution on large scans, joins, and decimal aggregations.
- Enable Photon directly on the Databricks SQL Warehouse or Interactive/Job cluster.


### Technique 5: Delta Table Compaction & Vacuuming
Stale unvacuumed files slow down driver metadata planning:

```sql
-- 1. Compact small files into ~1GB files
OPTIMIZE fact_orders;

-- 2. Clean up tombstoned files older than 7 days
VACUUM fact_orders RETAIN 168 HOURS;
```


## 3. Summary Optimization Matrix

| Technique | When to Apply | Expected Gain |
| :--- | :--- | :--- |
| **Liquid Clustering / Z-ORDER** | Multi-TB tables with multi-column queries (`date`, `customer_id`) | 10x - 100x I/O reduction |
| **Photon Vectorized Engine** | Compute-heavy analytical aggregations and scans | 3x - 8x faster CPU compute |
| **Data Skipping Config (`numIndexedCols`)**| Queries filtering on columns beyond the 32nd position | Restores file pruning |
| **Compaction (`OPTIMIZE` / `VACUUM`)** | Table suffers from millions of small uncompacted files | Reduces metadata lag |
