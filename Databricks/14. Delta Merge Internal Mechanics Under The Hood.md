# What Actually Happens Internally During a Delta MERGE?

## Question
Explain the internal execution mechanics of a Delta Lake `MERGE INTO` operation under the hood (2-pass scan, outer join, file rewriting, and commit).


## 1. The 2-Pass Architecture of Delta MERGE

```
[ Phase 1: Inner Join (Identification Pass) ]
  • Joins Source DataFrame with Target Delta Table metadata.
  • Identifies exactly which Target Parquet files contain matching rows (Candidate Files).
  • Unmatched target files are completely untouched and skipped.
                     │
                     ▼
[ Phase 2: Full Outer Join & Row Processing (Execution Pass) ]
  • Reads ONLY the Candidate Files from Target and joins with Source batch.
  • For MATCHED rows: Evaluates update/delete conditions.
  • For NOT MATCHED rows: Evaluates insert conditions.
  • For UNTOUCHED rows in candidate files: Preserves original row values.
                     │
                     ▼
[ Phase 3: Write New Parquet Files & Atomic Log Commit ]
  • Writes new Parquet files containing modified and preserved rows.
  • Commits a new JSON version in `_delta_log/` marking old candidate files as REMOVED (tombstoned)
    and newly created files as ADDED.
```


## 2. Low-Shuffle Merge Optimization (Databricks Photon)
In modern Databricks runtimes, **Low-Shuffle Merge** optimizes Phase 2 by separating unmodified rows from modified rows, rewriting only mutated data blocks to minimize I/O write amplification.
