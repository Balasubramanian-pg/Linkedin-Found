# Case Study: Resolving Real-World Join Data Skew

## Question
Describe a real-world data skew problem you encountered in production and walk through the exact code and configuration steps used to resolve it.


## 1. The Scenario
In an e-commerce platform, joining `FactOrders` (1 Billion rows) with `DimMerchants` (100K rows) was failing. A single merchant ("Amazon Global Store") accounted for **28% of all total orders**.
- 199 tasks completed in 15 seconds.
- 1 task processing the "Amazon" merchant ID ran for **2 hours** before failing with an executor OOM.


## 2. The Solution: Join Key Salting

```python
import pyspark.sql.functions as F

SALT_FACTOR = 16

# 1. Add uniform random salt (0 to 15) to large skewed orders table
df_orders_salted = df_orders.withColumn(
    "salt_key",
    F.concat(F.col("merchant_id"), F.lit("_"), F.floor(F.rand() * SALT_FACTOR))
)

# 2. Explode dimension table to replicate each merchant key across all 16 salts
df_merchants_exploded = (
    df_merchants
    .withColumn("salt_arr", F.array([F.lit(i) for i in range(SALT_FACTOR)]))
    .withColumn("salt_val", F.explode("salt_arr"))
    .withColumn("salt_key", F.concat(F.col("merchant_id"), F.lit("_"), F.col("salt_val")))
    .drop("salt_arr", "salt_val")
)

# 3. Perform balanced join across all 16 executor partitions
df_joined = df_orders_salted.join(df_merchants_exploded, on="salt_key", how="inner").drop("salt_key")
```
> **Result:** Stage runtime dropped from **2+ hours (OOM)** to **3 minutes 12 seconds**.
